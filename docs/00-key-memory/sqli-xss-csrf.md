# 题型 05 · SQL 注入 / XSS / CSRF 辨析与防御

> **本次原题**：某系统登录页与查询接口被判定同时存在 SQL 注入与存储型 XSS。请说明注入成因、最小载荷与生效原因、至少三层防御并指出根治手段、SQL 注入与 XSS 的本质区别、以及「已有 CSRF Token 为何仍被绕过」。
> **答案**：SQL 注入的成因是**输入被拼进语句、代码与数据没分离**，根治靠**预编译（参数化）**而不是关键字过滤；XSS 的成因是**输出未按上下文编码**，防御靠**上下文编码 + CSP + HttpOnly**；CSRF 的成因是**请求缺少不可伪造的凭据**，防御靠 **Token + SameSite + Origin/Referer + 二次验证**。XSS 之所以让 CSRF Token 失效，不是「击穿同源策略」，而是**脚本本就运行在同源上下文里**，能直接读取 Token。

## 一、识别信号（看到这些就是这类题）

- 题干出现 **登录框 / 查询接口 / 搜索框 / 留言板 / 富文本编辑器** 这些「有输入又被回显」的位置。
- 题干出现 **报错页、弹窗、cookie 被盗、会话劫持、Token、Referer、Origin、SameSite**。
- 题干把两个漏洞**放在一起问区别**，或问「为什么有 A 时 B 的防护失效」。
- 题干出现 **渗透报告、整改建议、代码审计发现**，要求在「代码层 / 配置层 / 运维层」给措施。
- 出现 **最小验证载荷** 字样，要求解释「为什么这条能生效」。

## 二、核心原理（3 分钟真正搞懂）

三者都源自「**信任了不可信输入**」，但危险的落点完全不同：

| 漏洞 | 恶意输入最终交给了谁 | 本质一句话 |
|------|----------------------|-----------|
| SQL 注入 | **数据库的 SQL 解释器**（服务端） | 输入变成了**指令** |
| XSS | **浏览器的 HTML/JS 解释器**（客户端） | 输入变成了**脚本** |
| CSRF | 谁都不注入 —— 借**用户浏览器的身份**发请求 | 输入不是重点，**「请求不是用户想发的」才是** |

判定口诀：**先问「字符串被谁执行」，再问「请求是谁发出的」。** 前者分 SQL 注入与 XSS，后者区分 CSRF。

三个根治点各自对应一句原理：

- **预编译**：语句模板先编译成语法树，参数只作为**数据绑定**，永不再参与语法解析 → 输入没有机会变成代码。
- **输出编码**：同一个字符在 HTML 正文、属性、JS 字符串、URL 里危险程度不同 → 按上下文转义，让浏览器**只当文字读**。
- **CSRF Token**：在请求里放一个**攻击者猜不到、且与会话绑定**的值 → 伪造请求带不上它。

## 三、通用解题步骤（照着套，5 步）

1. **定位注入点**：输入去了服务端拼串（SQL 注入）、被原样输出到页面（XSS）、还是被浏览器自动携带凭据发出（CSRF）。
2. **成因一句话**：代码与数据未分离 / 输出未编码 / 请求缺少不可伪造凭据。
3. **载荷 + 为什么生效**：引用闭合 → 注释截断 → 恒真条件，三步说明白，别只贴字符串。
4. **防御分层，并点出根治层**：根治（代码层）→ 收敛损失（权限/配置层）→ 兜底与发现（WAF/日志审计）。
5. **叠加场景画攻击链**：A 漏洞 → 拿到什么 → 使 B 的哪条假设失效 → 后果。

## 四、本题完整解答

**（1）SQL 注入的成因**

后端用**字符串拼接**构造 SQL，用户输入被当作语句的一部分交给数据库解析。危险的根不是「有特殊字符」，而是**代码与数据共用同一条解析通道**。

**（2）最小载荷与生效原因**

```sql
-- 原始语句
select * from users where username = '$u' and password = '$p'

-- 输入 admin' --（MySQL 中 -- 后必须跟空格）
select * from users where username = 'admin' -- ' and password = '$p'
```

生效三步：`'` **闭合**了原字符串边界 → `-- ` 把「密码校验」整段**注释掉** → 查询退化为「用户名是 admin 就返回记录」，密码条件消失。

拖库手法：`order by n` 递增探测列数 → `union select 1,2,3` 找回显位 → `union select username,password,4 from users` 经页面回显取出；无回显时走**盲注**（布尔、时间延迟、报错注入）。

**（3）三层防御与根治手段**

| 层 | 措施 | 作用 |
|:--:|------|------|
| 代码层（**根治**） | **预编译 / 参数化查询**、ORM 参数绑定 | 参数只作数据绑定，永不参与语法解析 |
| 代码层（辅助） | 输入类型与白名单校验、输出与错误信息不回显 | 减少可注入面、不给报错探路 |
| 权限与配置层 | 数据库**最小权限账户**、关闭详细报错、禁用危险函数 | 限制拖库损失上限 |
| 检测与兜底层 | WAF 虚拟补丁、SQL 审计日志与告警 | 拦已知攻击、留证据 |

**为什么参数化比关键字过滤可靠**：过滤是**事后猜特征**，可用大小写混写、`union/**/select`、等价表达式、编码变形绕过；参数化是**消除条件**——输入根本不进入解析器。

**（4）SQL 注入与 XSS 的四维对比**

| 维度 | SQL 注入 | XSS |
|------|----------|-----|
| 注入对象 | 数据库 **SQL 解释器** | 浏览器 **HTML/JS 解释器** |
| 执行位置 | **服务端**（数据库侧） | **客户端**（受害者浏览器） |
| 危害 | 数据泄露、篡改、删库、越权读写 | 窃取 Cookie/Session、钓鱼、页面篡改、蠕虫传播、配合 CSRF |
| 对应防御 | 预编译参数化、最小权限、关闭报错 | **按上下文输出编码**、CSP、HttpOnly、白名单过滤 |

**（5）为什么有 XSS 时 CSRF Token 失效**

CSRF 防护隐含假设：**攻击者读不到目标站点的页面内容**，所以拿不到 Token。而 XSS 脚本运行在目标站点**同源上下文**中，可以直接 `document` 读取页面里的 Token，再携带它发起请求——攻击者不是撬门，而是**已经站在屋里拿着钥匙**。

要点纠正：**不是「XSS 击穿了同源策略」**。同源策略只限制「读取响应」，**从不阻止请求发出**，所以 CSRF 本来也不需要击穿它。XSS 绕过的不是同源策略，而是「攻击者无法读取页面」这条假设。

## 五、变式训练（先自己做，再展开答案）

<details>
<summary>变式 1：为什么 `#` 也能注释掉后半句？</summary>

在 MySQL 中 `#` 与 `-- `（连字符后必须跟空格）都是行注释符；`/* */` 是块注释。所以 `admin'#`、`admin'-- `、`admin'/**/` 都能截断后续条件。考试若写错注释符格式（如 `--` 后不加空格）会被判细节错误。
</details>

<details>
<summary>变式 2：预编译为什么能根治，而不是「更难绕过」？</summary>

预编译把 SQL 先编译成**语法树与执行计划**，占位符位置固定；参数在绑定阶段只被当作**值**塞进去，不再经过词法与语法解析。因此无论参数里有多少引号、`union`、注释符，都只是一段字符串数据。**这不是对抗强度的问题，而是攻击面被消除。**
</details>

<details>
<summary>变式 3：存储型 XSS 与反射型 XSS 的区别，防御上有何不同？</summary>

反射型：载荷来自当前请求，被服务端原样回显，需诱导受害者点击恶意链接，不落地。存储型：载荷被写入数据库（留言、昵称、评论），所有访问该页面的用户都会中招，危害面最广，可蠕虫式传播。防御核心相同——**输出时按上下文编码**；存储型额外需要**入库前的富文本白名单净化**（如 DOMPurify）与**内容审核**。
</details>

<details>
<summary>变式 4：CSRF 的四种防御，各防的是哪一环？</summary>

① **CSRF Token**（与会话绑定、不可预测、必要时一次性）——攻击者拿不到凭据；② **SameSite Cookie**（Lax/Strict）——跨站请求不携带 Cookie；③ **校验 Origin/Referer**——请求来源不是本站就拒绝；④ **关键操作二次验证**（密码、验证码、U2F）——即使请求被伪造也无法完成。注意：以上在**存在 XSS 时都会削弱或失效**，因为脚本在同源内可直接读取/伪造。
</details>

<details>
<summary>变式 5：为什么说 XSS 的危害等级高于 CSRF？</summary>

CSRF 只能「以受害者身份发请求」，且**读不到响应**，攻击面受限于可被伪造的操作；XSS 能读取页面全部内容（含 Token、个人信息）、可发起任意请求、可篡改界面钓鱼、可持久化并横向传播。所以 XSS 是「获得同源执行权限」，CSRF 只是「借用一次请求」。
</details>

## 六、易错点与陷阱

- **把关键字过滤/正则当根治**：只能对抗症状，能被编码与注释变形绕过。根治只有预编译。
- **说 XSS 在后端执行**：XSS 只在**浏览器**执行，后端只是没做输出编码的转发者。
- **用 CSRF Token 防 XSS**：Token 防的是伪造请求，防不了同源脚本读取。
- **说 XSS「击穿同源策略」**：同源策略不阻止请求发出，XSS 是**绕过了「攻击者读不到页面」这条假设**，它本身就在同源内。
- **只写「输入校验」不写「输出编码」**：XSS 的主战场在输出侧，且必须按上下文编码。
- **漏掉 HttpOnly 与 CSP**：这两条是 XSS 的「减损」措施，与编码同等重要。
- **载荷不解释机理**：只贴 `' or '1'='1` 不说「闭合 + 注释 + 恒真」，拿不到这一问的分。

## 七、考点速记卡（复习只看这一块）

**一句话分开三者**：注入看「谁在执行字符串」，跨站看「请求是谁发出的」。

| 项 | SQL 注入 | XSS | CSRF |
|----|----------|-----|------|
| 恶意输入交给谁 | 数据库 SQL 解释器 | 浏览器 JS 解释器 | 不注入，借浏览器身份发请求 |
| 执行位置 | 服务端 | **客户端** | 受害者浏览器发请求 |
| 核心成因 | 代码与数据未分离 | 输出未按上下文编码 | 请求缺少不可伪造凭据 |
| 根治手段 | **预编译 / 参数化** | **上下文输出编码** | **不可预测 Token** |
| 辅助措施 | 最小权限、关报错、WAF、审计 | CSP、HttpOnly、白名单、DOMPurify | SameSite、Origin/Referer、二次验证 |
| 典型危害 | 拖库、改库、删库 | 盗 Cookie、钓鱼、篡改、蠕虫 | 以受害者身份完成操作 |

**三句口诀**

1. **参数化 = 让输入永远没机会变成代码。**
2. **SQL 注入治本靠预编译，XSS 治本靠编码，CSRF 治本靠 Token。**
3. **XSS 不在门外撬锁，它已经在屋里**——所以 Token、同源策略都挡不住它。
